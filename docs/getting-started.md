# Set up and edit the AIX website

This guide is for contributors who want to add or update website content. The site is generated by Jekyll from Markdown files. You edit source files; Jekyll rebuilds the pages.

## 1. Get the project

Install Git and a text editor if you do not have them. Clone the main repository using your normal Git access:

```sh
git clone https://github.com/semantic-systems/aix.leuphana.de.git
cd aix.leuphana.de
```

Open this root folder (the one containing `_config.yml`, `Gemfile`, and `docker-compose.yml`) in your editor. If you already have a checkout, do not clone it again; update it through your team's normal Git workflow. Work on a branch so the change can be reviewed before it reaches `main`. For example, after updating your checkout, use `git switch -c docs/update-team-profile` for a documentation change. If you do not have write access to the main repository, use a fork and open a pull request from it.

## 2. Preview the site

### Docker (simplest)

Install Docker Desktop or a compatible Docker installation with Compose, and start Docker. From the project root, run:

```sh
docker compose up jekyll
```

Wait for the service to start, then visit <http://localhost:4000>. Saving a content file should trigger a rebuild. Stop with Ctrl+C. If you change `_config.yml`, restart the server; Jekyll does not reload configuration automatically. Running only `jekyll` avoids starting the crawler.

### Local Ruby alternative

If Ruby and Bundler are already installed, run these from the project root. The deployment workflow uses Ruby 3.2; using the same major/minor version locally helps keep behavior consistent:

```sh
bundle install
bundle exec jekyll serve
```

Open <http://localhost:4000>. This uses dependencies in `Gemfile` and `Gemfile.lock`. If installation fails, use Docker or ask a maintainer to check the Ruby setup.

## 3. Choose the right content folder

| Content | Folder | Instructions |
| --- | --- | --- |
| News | `_posts/` | [Posts](posts.md) |
| Research projects | `_projects/` | [Projects](projects.md) |
| Papers | `_publications/` | [Publications](publications.md) |
| People | `_team/` | [Team](team.md) |
| Interactive demos | `_demos/` | [Demos](demos.md) |

Copy the template in that folder to a new `.md` file. Use a lowercase, hyphenated filename without spaces. News files are different: they must begin with `YYYY-MM-DD-`. Do not edit a template to create a real item.

## 4. Fill in front matter and body

The block between the first two `---` lines is YAML **front matter**. It supplies fields such as the title, date, image, and layout. The rest of the file is the visible page body. Keep the opening and closing `---` lines, use spaces rather than tabs, and indent list items consistently. Quote values containing punctuation such as `:`. Dates should be `YYYY-MM-DD`; publication `year` is a four-digit number. Do not leave example domains, names, or placeholder text in published content.

For a new item, keep `published: false` while writing. Once reviewed, set `published: true`. If the field is absent, Jekyll can treat the item as publishable, so use an explicit `false` for drafts. A future dated news post is hidden by Jekyll even if `published: true`.

Write a short opening paragraph and use `##` for main sections. Standard Markdown supports links, lists, and images. For example:

```md
## Results

The team released a new dataset. Read the [project documentation](https://example.org).

![Researchers discussing the project]({{ '/assets/images/project-meeting.jpg' | relative_url }})
```

Replace example paths and links. See [the image guide](images.md) for file placement, captions, and display rules.

## 5. Review locally

1. Keep `published: false` while drafting. A hidden draft has no rendered detail page. When you are ready to inspect it locally, temporarily change it to `published: true` in your branch and wait for Jekyll to rebuild.
2. Open the appropriate list page: `/news/`, `/projects/`, `/publications/`, `/team/`, or `/demos/`. Open the new detail page and check the title, dates, text, links, and image.
3. Check narrow/mobile width if possible. Long titles, wide images, and tables can affect the layout.
4. For projects, search by the title and a project member. For papers, search by the title and an author. For team profiles, check the automatically linked projects and publications.
5. If the item is still a draft, change it back to `published: false` before committing. When it is approved for publication, leave it `true`, preview once more, and include that change in the reviewed commit.

If a page does not appear, check the filename, `published`, the news date, YAML indentation, and the build log. If an image is missing, check its exact filename, extension, letter case, and path. Use URLs starting with `/assets/`; do not use a path from your own computer.

## Publish a change

Commit the source file and any new image together. Before committing, review changed filenames so you do not include cache files or unrelated local changes. Open a pull request or follow the team's review process. The repository's [deployment workflow](../.github/workflows/deploy.yml) runs Python checks and a Jekyll build on pushes to `main`, then updates the VPS. A green local preview does not publish anything until the change reaches `main` and the workflow succeeds. Check the workflow result and the live page after deployment.

The crawler in `docker-compose.yml` is a separate service that can update publication files and check external links. It uses network access and `.env` for email settings. Do not run it just to preview editorial changes; publication maintainers should review its generated file changes before committing.
See [broken-link notifications](link-checker.md) to assign a page owner and configure who receives alerts.
